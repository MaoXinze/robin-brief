# 02 · 系统架构

## 2.1 分层架构

```
┌────────────────────────────────────────────────────────────┐
│  接入层  CLI（typer）: robin run / demo / schedule / archive │
├────────────────────────────────────────────────────────────┤
│  编排层  LangGraph 状态图                                    │
│          状态 BriefState（blackboard）+ 条件边 + Send 并行    │
│          checkpoint（SqliteSaver / InMemorySaver）           │
├────────────────────────────────────────────────────────────┤
│  Agent 层  9 个节点（工厂函数注入依赖）                        │
│   采集记者 → 去重管理员 → 分类编辑 → 评分编辑 → 摘要主笔        │
│   → 头条编辑 ─┬─ 深度评论员                                   │
│              └─ 快讯编辑 → 出版发行                            │
├────────────────────────────────────────────────────────────┤
│  能力层                                                      │
│   sources/  源适配器（RSS · HN · ArXiv · GitHub Trending）    │
│   llm.py    LLM 客户端（DeepSeek / Mock，结构化输出+重试）      │
│   store/    SQLite 归档（文章/日报/运行记录）                  │
│   render/   Jinja2 渲染（晨光纸感模板）                        │
│   push/     飞书 Webhook（卡片 + 加签）                       │
├────────────────────────────────────────────────────────────┤
│  基础设施  .env（ROBIN_* 环境变量）· sources.yaml · prompts/  │
└────────────────────────────────────────────────────────────┘
```

## 2.2 一次运行的完整数据流

```
1. run_pipeline(settings)
     ├─ 加载 sources.yaml → [SourceCfg]
     ├─ Database 打开，取近3天标题归一（跨天去重用）+ 昨日头条（昨日回顾用）
     └─ 组装初始 BriefState（run_date / window_hours / history_norms / ...）

2. START ──(条件边)──► dispatch_collect 返回 [Send(...)] ×N
     └─ LangGraph 并行执行 N 个 fetch_source（async，httpx）
          ├─ 成功 → articles: list[Article]（reducer: operator.add 汇聚）
          └─ 失败 → source_errors 追加一条（错误隔离，不影响其他源）

3. dedup：四层去重 → deduped + dedup_stats（漏斗）
     └─ 条数 < min_articles ──► relax（放宽窗口/阈值）──► 再次 fan-out（仅一次）

4. classify：LLM 结构化输出 → EnrichedArticle(category, companies)
     └─ is_ai=false 的条目直接丢弃

5. score：规则引擎打分 → LLM 批量校准(±1星) → importance + score_reason

6. summarize：批量一句话摘要（严格基于原文）

7. 并行编辑层（editor ‖ analyst，quicknews 串在 editor 后）
     ├─ editor  → headlines(含点评) + epigraph（今日微语）
     ├─ analyst → analysis（背景+影响）
     └─ quicknews（读 editor 结果做排除）→ quick_news
     ※ 三节点各写 stage_done 完成标志；publish 做幂等守卫（见 4.4）

8. publish：组装 BriefDocument → Jinja2 渲染 HTML/MD
     → SQLite 归档 → 飞书推送（可选）

9. run_pipeline 汇总 → RunReport（漏斗/耗时/token）→ run_report.json
```

## 2.3 技术选型对比（为什么这么选）

### 编排框架：LangGraph vs CrewAI vs 自研

| 维度 | LangGraph ✅ | CrewAI | 自研编排 |
|---|---|---|---|
| 编排模型 | 状态图（blackboard）+ 显式拓扑 | 角色对话流水线 | 自定义 |
| 并行能力 | Send 动态 map / 并行节点 / 条件边原生支持 | 弱 | 要自己写 |
| 断点恢复 | checkpoint 内置 | 无 | 要自己写 |
| 流程控制 | 条件边（宽松重采循环）、幂等守卫可表达 | 顺序为主 | 灵活但全要自己造 |
| 可讲深度 | 状态机、reducer、超步语义 | 使用层 | 最深但成本高 |

选 LangGraph 的决定性理由：本项目天然是**带条件循环的数据流水线**（去重后条数不足要回炉重采），状态图 + 条件边是精确匹配的抽象；且 checkpoint、并行、reducer 都是现成能力，工程精力可以花在业务逻辑上。

### LLM：为什么默认 DeepSeek

- OpenAI 兼容接口 → 客户端层零适配可换任何供应商（Kimi/GLM/OpenAI）
- 价格低：单次完整出报约 1~2 万 token，日更场景成本可忽略
- JSON mode 支持稳定，配合 pydantic 校验 + 重试可靠性足够

### 去重：为什么不用向量库（与参考方案的差异）

参考方案建议"向量数据库语义去重"。实测三个问题：
1. DeepSeek 无 embeddings 端点，引入第二家供应商只为去重，依赖不值
2. 日更场景条目量（几十~几百）远达不到向量库的性能/规模收益
3. 规则层能解决 90%+（同事件转载标题高度雷同），剩下临界对交给 LLM 裁决更准

最终方案：**URL 精确 → 标题归一精确 → rapidfuzz partial_ratio 模糊（≥92 判重 / 82~92 LLM 裁决）→ 近 3 天历史库**。中文标题归一后无空格分词，token 类算法失效，故用 partial_ratio（详见 08-开发日志）。

### 存储：为什么 SQLite 而不是 PostgreSQL+Redis

- 单机日更场景，写入量极小；SQLite WAL 模式足够
- 零运维、零部署依赖——"简历项目"能在任何机器 5 分钟跑起来本身就是工程判断
- 表结构（articles/briefs/runs）与 SQL 访问层已隔离，未来换 PG 只动 store/db.py

### 渲染：为什么 Jinja2 + 纯 CSS 而不是前端框架

- 日报是"内容几乎不变、版式高度定制"的静态页面，框架是负资产
- 无外部资源（无 CDN/字体/JS），离线可渲染、打印友好
- 内容与呈现分离：Agent 产物是结构化 BriefDocument，模板只是视图

## 2.4 关键设计决策速查表

| 决策 | 选择 | 一句话理由 |
|---|---|---|
| 快讯是否再调 LLM 润色 | 否，复用摘要 | 省 token；口径一致 |
| GitHub Trending 是否可进头条 | 否（headline_eligible=false） | 热度高但新闻性弱，只进快讯 |
| 热度加成上限 | min(0.25, log10(points+1)×0.12) | 热度是信号，不应盖过事件重要性 |
| 头条不足 3 条怎么办 | 按评分直选补齐（降级保证） | 报纸每天必须出 |
| 分类批次失败怎么办 | 整块降级为 other，不中断 | 报纸每天必须出 |
| publish 多次触发 | stage_done 完成标志 + 幂等守卫 | 防飞书重复推送（见 08 日志） |
| checkpoint | 真实跑 AsyncSqliteSaver，mock 用 InMemory | 图以 ainvoke 驱动，检查点必须支持异步 |
