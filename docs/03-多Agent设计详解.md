# 03 · 多 Agent 设计详解

> 所有 Agent 节点都是**工厂函数**：`make_xxx_agent(llm, settings, ...)` 返回图节点。
> 依赖（LLM 客户端、配置、数据库）显式注入，节点本身保持纯粹 —— 这是可测试性的关键。

## 3.0 通用约定

**结构化输出契约**：每个 LLM Agent 都有对应的 pydantic Schema（`agents/schemas.py`）。LLM 返回的 JSON 必须通过校验，失败自动重试（重试时把校验错误回示给模型），重试耗尽抛 `LLMError`，由节点降级策略接管。

**提示词组织**：`prompts/*.txt` 独立文件，职责与规则写在提示词里，JSON 载荷用 `<input>...</input>` 标签附加在尾部 —— 规则与数据分离，mock 客户端依赖该约定稳定提取输入。

**三段式降级**：每个 LLM 节点都定义了"LLM 失败时怎么办"（见各节），保证报纸每天必须出。

## 3.1 采集记者 Collector

| | |
|---|---|
| 职责 | 并行抓取所有启用数据源，归一化为 `Article` |
| 输入 | Send 载荷 `{source, relaxed, window_hours, now}` |
| 输出 | `articles`（reducer 汇聚）、`source_stats`、`source_errors` |
| LLM | 不用 |
| 失败处理 | try/except 包住单个源：错误记入 `source_errors`，其他源不受影响 |

**LangGraph 用法**：`dispatch_collect` 是条件边上的路由函数，返回 `Send("fetch_source", payload)` 列表 —— 动态 map：源数量由配置决定，LangGraph 并行执行全部实例，reducer `operator.add` 自动汇聚多路结果。

**宽松重采（relaxed）**：`relax_refetch` 节点把窗口从 30h 放宽到 72h、HN points 阈值减半、GitHub 关键词过滤放行，然后条件边把流程送回 fan-out —— 这是图里唯一的循环，`retry_count` 保证最多一次。

## 3.2 去重管理员 Deduplicator

四层漏斗（每层的通过数都进漏斗统计）：

```
collected（原始）
  → after_url      第1层：规范化 URL 精确去重（utm/尾斜杠/www 归一后 sha1）
  → after_title    第2层：标题归一精确去重（只留中英文数字，小写）
  → after_fuzzy    第3层：rapidfuzz partial_ratio
                     ≥92 直接判重；82~92 临界对 → LLM 裁决；<82 保留
  → after_history  第4层：对比近 3 天历史库（≥93 判重）—— 昨天报过的事今天不再报
kept
```

**排序即策略**：进入去重前先按 `(-来源权重, -热度, -时间)` 排序，重复时保留高权重来源的版本。

**LLM 裁决**（`prompts/dedup.txt`）：输入临界对的双方标题与相似度，判断"是否同一事件"，规则：同事件 → true；仅主题相近 → false；不确定倾向 false（宁可保留不误杀）。

**关键实现细节**：中文标题归一后没有空格，token 类相似度算法（token_set_ratio）失效，必须用 `partial_ratio` —— 这是开发中实测发现的坑（详见 08-开发日志 §3）。

## 3.3 分类编辑 Classifier

| | |
|---|---|
| 职责 | 打类别标签 + 识别涉及公司 + 过滤非 AI 内容 |
| 输入 | `[{id, title, content[:500]}]`（20 条/批） |
| 输出 | `[{id, category, companies[], is_ai}]` |
| 降级 | 批次 LLM 失败 → 整块按 `other` 处理，不中断 |

**七类标签体系**：模型发布 / 融资并购 / 产品动态 / 政策监管 / 开源动态 / 研究论文 / 其他。类别直接影响评分权重，也是日报上的分类签。

**is_ai 过滤**：明显与 AI/科技无关的条目（源里混入的社会新闻等）在此丢弃 —— 把"过滤"放在分类里而不是独立节点，一次 LLM 调用完成两件事。

## 3.4 评分编辑 Scorer

**两段式设计（本项目的核心可解释性设计）**：

```
规则引擎（确定性，可测试，零成本）
  rule_score = 0.55 × 事件类型权重
             + 0.30 × 公司权重（取候选中最高者，无知名公司记 2.5）
             + 0.10 × 时效系数（≤6h=1.0 ... >48h=0.5）
             + min(0.25, log10(热度+1) × 0.12)      ← 热度加成有上限
  → 取整到 1~5
LLM 校准（批量）
  允许 ±1 星微调 + 写一句评分理由（随日报展示）
```

| 权重表 | 高权重项 |
|---|---|
| 事件类型 | 模型发布 4.5 · 融资并购 4.5 · 政策监管 4.0 · 产品 3.5 · 开源 3.0 · 研究 2.5 |
| 公司 | OpenAI/Anthropic/NVIDIA 5.0 · Google/DeepSeek 4.5 · Meta/微软/月之暗面/智谱/阿里/腾讯/字节 4.0 · … |

**设计理由**：规则主导保证可解释（每条星级都有理由可查）与可测试（纯函数单测）；LLM 校准提供语义灵活性。热度加成设上限是实测教训——GitHub 6 万星仓库曾把真正的行业大事挤出头条（见 08-开发日志 §4）。

## 3.5 摘要主笔 Summarizer

| | |
|---|---|
| 职责 | 一句话中文摘要（≤60 字），快讯直接复用 |
| 输入 | `[{id, title, content[:800]}]`（10 条/批，控制单次上下文） |
| 降级 | 批次失败 → 标题截断兜底 |

Prompt 约束（对应"可信度优先"）：信息密度优先（谁+做了什么+关键数字）；**不得编造原文没有的数字与事实**；英文原文翻译成中文，专有名词保留。

## 3.6 头条编辑 Editor（主编视角）

| | |
|---|---|
| 职责 | 三件事：选 3~5 条头条 / 写「为什么重要」点评 / 写今日微语 |
| 输入 | 评分排序后的前 25 条候选（含摘要、类别、公司、星级） |
| 输出 | `EditorialPlan{headlines:[{id, comment}], epigraph}` |
| 降级 | LLM 失败 → 按评分直选 + 模板点评，**报纸必须出** |

**三条编辑方针**（写进 Prompt 与代码）：
1. importance 优先，同分看事件类型/公司权重；同一事件的多条报道只保留信息量最大的一条
2. 点评回答"为什么重要"（影响/趋势判断），不复述标题、不编造 —— 这是日报的核心价值
3. 今日微语基于第 1 条头条的视角，"是洞察不是鸡汤"

**headline_eligible 机制**：数据源可配置 `headline_eligible: false`（GitHub Trending），其条目只进快讯 —— 热度高但新闻性弱，不该抢头条。

## 3.7 深度评论员 Analyst

| | |
|---|---|
| 职责 | 对 1~2 个最大事件（importance≥4，按类别去重）写深度解读 |
| 输出 | 每事件 `{background(背景,120~200字), impact(影响,80~150字)}` |
| 约束 | 只可基于输入信息与公认公开背景，不得编造具体数字、引语和时间点 |

## 3.8 快讯编辑 QuickNews

**设计决策：零 LLM 调用**。快讯 = 摘要主笔产物的直接复用（摘要本来就是 ≤60 字的一句话），按重要性排序取 15 条 —— 快讯的价值在扫读效率，不在于与摘要措辞不同。

依赖关系：快讯必须排除已进头条的条目，因此图上 **editor → quicknews** 是顺序边（同一超步并行读不到彼此输出，这是 LangGraph 并行语义的实战细节，见 08-开发日志 §5）。

## 3.9 出版发行 Publisher

唯一有副作用的节点：组装 `BriefDocument` → Jinja2 渲染 HTML/Markdown → SQLite 归档（文章+日报）→ 飞书推送（可选）→ 产出路径供 RunReport 记录。

**幂等守卫**：editor/analyst/quicknews 各写 `stage_done` 完成标志；publish 发现标志不全（被 LangGraph 提前触发）则跳过本次 —— 防止飞书重复推送（见 08-开发日志 §5）。

## 3.10 MockLLMClient：离线的"伪编辑部"

`MockLLMClient` 与 `DeepSeekClient` 实现同一接口，按 agent 名路由到规则式实现（`agents/mock_impl.py`）：

- 分类：关键词表（中英文）→ 类别 + 公司识别 + AI 相关性
- 评分：直接采纳规则分，理由用模板拼装
- 摘要：正文第一句（≥12 字）否则标题，截断 60 字
- 头条：按（星级，热度）排序选前 N，点评按类别模板轮换，微语按头条类别选
- 去重裁决：相似度 ≥87，或「同公司 + 同产品代号（V4/GPT-5/GB300…）」判同事件

价值：① 无 API Key 一条命令出样报；② 端到端测试确定可断言；③ 真实链路的降级路径被持续演练。
