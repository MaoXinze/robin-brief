## 6.2 高频面试题与参考回答

**Q1：为什么用 LangGraph 而不是 CrewAI / AutoGen？**
> 考察点：技术选型论证。答：我的场景是"带条件循环的数据流水线"——去重后条数不足要回炉重采，这是状态机问题。LangGraph 的显式状态图 + 条件边精确匹配；Send API 做动态并行采集；checkpoint 免费获得断点恢复。CrewAI 是角色对话抽象，流程控制（循环、条件路由）表达能力弱；AutoGen 偏对话式协作，我这个场景 Agent 之间不对话，共享的是状态黑板。自研编排我也考虑过，并行调度和 checkpoint 要自己造，工程精力应该花在业务上。

**Q2：9 个 Agent 是不是过度设计？一个 Prompt 链不行吗？**
> 考察点：架构判断。答：三个理由。① 职责单一才能独立调优：改分类标准只动分类提示词，不碰写作提示词；② 可观测：漏斗按 Agent 粒度记录，哪里坏了一眼看出；③ 成本分层：去重裁决和评分校准用小批量调用，摘要按 10 条一批，editor/analyst 各一次——如果合成一个大 Prompt，每次迭代都要重新调全部环节。不过我也承认部分 Agent 很薄（快讯编辑零 LLM 调用，只做筛序），拆开是为了流程语义清晰而不是凑数。

**Q3：去重为什么不用向量/embedding？**
> 考察点：技术方案的现实约束意识。答：算过账：① 默认供应商 DeepSeek 没有 embeddings 端点，为去重引入第二家供应商不值；② 日更条目量几十到几百，远够不着向量库的规模收益；③ 实测同事件转载标题高度雷同，规则层（URL/标题归一）解决 90%+，真正难的是"字面不同但同事件"的临界对——这个交给 LLM 语义裁决比 embedding 余弦阈值更可控（还能输出理由）。embedding 方案写在 Roadmap，等接入需要它的场景（个性化订阅去重）再上。

**Q4：中文标题去重有什么特别的坑？**
> 考察点：真实动手经验。答：我一开始用 rapidfuzz 默认的 token_set_ratio，上线测试发现中文同事件标题相似度只有 60 多——因为归一化后中文没有空格，整个标题是一个"token"，token 类算法退化。换成 partial_ratio（最长公共子串视角）后，"DeepSeek 发布 V4 大模型：推理成本再降60%" 和它的转载版本能到 95+。另外还踩过 URL 归一化的坑：无查询参数的 URL 被拼上了 None 字符串导致同一 URL 哈希不同——单测抓住了。

**Q5：LLM 输出不合法 JSON 怎么办？**
> 考察点：工程可靠性。答：三层。① 所有 LLM 调用走 pydantic Schema 校验的结构化输出，失败把校验错误回示给模型重试（最多 3 次）；② 重试耗尽抛 LLMError，每个节点有自己的降级策略——分类失败降为 other、评分退回规则分、摘要退回标题截断、头条按评分直选，核心原则是"报纸每天必须出"；③ 降级事件进运行报告，事后可归因。

**Q6：怎么防止 LLM 幻觉污染日报？**
> 考察点：LLM 应用的可信度设计。答：三道防线。① 摘要/点评的 Prompt 明确"必须基于原文，不得编造数字与事实"，且摘要输入就是抓取到的原文；② 每条内容保留来源名和原文链接，读者可回溯验证；③ 重要性评分由确定性规则引擎主导（可解释、可单测），LLM 只做 ±1 星校准，且评分理由随日报展示。设计哲学是：LLM 负责"语言"，规则负责"排序与判断的底线"。

**Q7：评分为什么不让 LLM 直接打分？**
> 考察点：LLM 与传统工程的边界。答：纯 LLM 评分三个问题：不可回归测试、同一输入可能不同输出、成本高。我的公式是 0.55×事件类型权重 + 0.30×公司权重 + 0.10×时效 + 有上限的热度加成——每个系数都可解释、可单测、可回归。LLM 在这之上做 ±1 星语义校准（比如同一事件在不同上下文里的分量）。实测还有个教训：GitHub 6 万星仓库的热度加成曾把真正的行业大事挤出头条，所以热度加成设了 0.25 的上限——这是调参出来的设计。

**Q8：并行采集的错误隔离怎么做的？**
> 考察点：分布式/并发基础。答：采集用 LangGraph 的 Send 动态 map，每个源一个并行任务，任务内部完整 try/except——失败只往 state 的 source_errors 追加一条（用 reducer 合并），成功路径写 articles。所以单源 404/超时只损失该源，漏斗和报告里能看到。专门有一个测试用"某源 404"的 mock 断言其余源照常出版。

**Q9：端到端测试怎么做的？不连 LLM 和外网怎么测全链路？**
> 考察点：测试策略。答：两个边界做成可注入依赖：网络层是 httpx 客户端工厂（测试注入 MockTransport，路由到真实源结构录制的 fixtures）；LLM 层是客户端接口（测试/Mock 模式注入规则式的 MockLLMClient，输出确定性结构且经过同样的 pydantic 校验）。于是端到端测试跑的是和生产完全相同的 LangGraph 流水线，只换了两个边界——33 个用例离线 1.5 秒跑完，包括宽松重采循环、单源故障隔离、昨日回顾这些路径。

**Q10：LangGraph 并行节点有什么坑？**
> 考察点：框架深度使用经验。答：两个实战细节。① 同一超步的并行节点读不到彼此的输出——快讯编辑要排除头条条目，但快讯和头条编辑并行时拿不到头条结果，所以图上把快讯设计成头条编辑的下游；② 多入边汇聚的节点可能被多次触发——publish 有三条入边，实际观察到执行了两次，第一次快讯还没合并，这会导致飞书重复推送。解法是每个编辑节点写完成标志（stage_done），publish 做幂等守卫，标志齐了才真正出版。

**Q11：checkpoint 有什么用？你的场景真的需要吗？**
> 答：SqliteSaver 把每个超步的状态落盘，进程挂了可从最近检查点恢复（thread_id 按日期）。我的场景里它更多是保险——单次运行几分钟，全损重跑成本也不高；但如果未来源数量涨到几十个、单次运行 30 分钟，checkpoint 就是刚需。mock 模式我显式用 InMemorySaver，演示零落盘。

**Q12：如果要支持 100 个数据源，架构要改哪里？**
> 答：分三层说。采集层：Send 并行天然支持，但要加并发上限（信号量）和每源限速，避免同时打满对方；抓取改异步队列（如 Celery）把"抓"和"算"解耦。智能层：分类/摘要已经是分批的，把批大小调优即可；去重的模糊比对是 O(n²)，百量级没问题，千量级要换倒排/SimHash 预筛。存储层：SQLite 换 PostgreSQL（store 层已隔离，只动一个文件）。这个项目的好处是这些演进点都有清晰的缝。

**Q13：这个系统的成本是多少？**
> 答：以 DeepSeek 计，单次完整出报约 1~2 万 token（7 次左右调用：分类/评分/摘要分批 + 裁决 + 编辑 + 解读按事件），日更月成本约几毛到一两块人民币；mock 模式零成本。运行报告里有每次的精确 token 数——成本可观测本身就是设计目标。

**Q14：日报的"今日微语"是营销文案吗？**
> 答：不是。Prompt 里明确要求"基于第 1 条头条的视角、是洞察不是鸡汤"，它是编辑对当天最重要事件的一句话态度——人工日报里主编寄语的角色。这是产品人格化的小设计。

**Q15：你如何继续提升这个项目？（展示规划能力）**
> 答：Roadmap 按价值排序：① 评测集——对分类/评分做人工标注，量化 Agent 质量，这是从"能用"到"可信"的关键；② FastAPI 归档站 + 个性化订阅——数据都在 SQLite，接口层半天工作量；③ GitHub Actions 定时——免服务器日更；④ 长图导出——报纸风分享到朋友圈的最后一公里。每个方向我都写了动机和预估工作量（docs/07）。

## 6.3 可能被追问的"压力问题"

**Q：这不就是调 API 吗，技术含量在哪？**
> 调 API 只是最后一层。技术含量在：状态图建模（循环、并行、幂等）、中文文本处理的真实坑（分词失效、URL 归一）、可靠性设计（结构化输出+重试+三段式降级+错误隔离）、可测试性（双边界注入让全链路离线可测）、可观测（漏斗+耗时+token）。这些都是"让 LLM 能力变成可靠系统"的工程，也是 LLM 应用工程师的核心工作。

**Q：个人项目没有真实用户，怎么证明价值？**
> 我给自己定义了可验证的成功标准：一条命令离线出报（演示可复现）、33 个测试全绿（质量可回归）、运行报告量化每个环节（效果可观测）、单源故障演示（健壮性可验证）。另外它真的在我机器上每天跑——连续性本身就是证据。

## 6.4 简历写作注意事项

1. **不要写"使用了 LangGraph/CrewAI 框架"就完事**——面试官必问"为什么"，用 6.2 Q1 的论证
2. **量化**：9 个 Agent、7 类源、33 个测试、4 层去重、3 道防线——数字比形容词有力
3. **留钩子**：简历上写"宽松重采闭环""热度加成上限"这类具体设计，引导面试官问到准备好的故事
4. **诚实边界**：被问到没做的部分（如分布式、高并发）直接说"当前规模不需要，但演进路径是 XX"——参考 Q12 的答法
