# 08 · 开发日志

> 记录真实开发过程中的设计决策与踩坑——面试里"你遇到过什么难问题"的素材库。

## §1 环境与选型阶段

**Python 3.14 vs 3.12**：本机默认 Python 是 3.14，但主流 LLM/编排生态的编译型依赖（pydantic-core 等）在最新解释器上的 wheel 覆盖存在滞后风险。项目用 uv 锁定 CPython 3.12.13 创建 venv——兼容性优先于尝鲜，uv 让这个决策的成本几乎为零。

**依赖极简原则**：放弃了参考方案里的 Scrapy + Playwright（重、难离线测试），采集用 httpx + feedparser + selectolax 三件套；数据库放弃 PostgreSQL + Redis 组合选 SQLite。判断依据：日更、单机、几十条数据的规模下，重组件只有负收益。**选型要按真实规模算账，不是按简历关键词堆料。**

## §2 LangGraph 使用的三个真实坑

**坑 1：Send 必须挂在条件边上。**
最初把 `dispatch_collect`（返回 Send 列表的函数）注册为普通节点，运行即抛 `InvalidUpdateError: Expected dict, got [Send(...)]`——普通节点的返回值必须是 state 更新字典，只有条件边的路由函数可以返回 Send 列表实现动态 map。改法：`add_conditional_edges(START, dispatch_collect)`。

**坑 2：异步节点与同步调用。**
采集节点是 async（httpx），`graph.invoke()` 直接抛 "No synchronous function provided"。统一改用 `asyncio.run(graph.ainvoke(...))`——让整个图走异步执行，同步节点由框架适配。

**坑 3：多入边汇聚节点会被多次触发。**
publish 有 editor/analyst/quicknews 三条入边，日志显示它执行了两次：第一次（editor+analyst 完成时）快讯还没合并，第二次才带全量数据。后果不只是脏日志——飞书会重复推送。解法：三个编辑节点各写 `stage_done` 完成标志（dict 合并 reducer），publish 做幂等守卫，标志齐备才执行。**"框架的隐式语义要用日志和断言验证，不能想当然。"**

## §3 中文文本处理的两个实测坑

**URL 归一化的 None 拼接**：`normalize_url` 用正则解构 URL 后直接 f-string 拼接，无查询参数时 query 组是 `None`，结果变成 `https://example.com/xNone`——同一个 URL 生成两个哈希，URL 去重层失效。教训：**解析重组类函数对"缺省组"必须显式处理**；单测第一轮就抓到了。

**中文标题不能用 token 类相似度**：rapidfuzz 的 token_set_ratio 按空格分词，而中文标题归一化后没有空格，整个标题变成一个 token，同事件标题相似度被低估到 60+。换 `partial_ratio`（最长公共子串视角）后："DeepSeek 正式发布 V4 大模型：推理成本再降60%" vs 转载版能到 95+。阈值体系随之重标定：≥92 判重 / 82~92 LLM 裁决 / <82 保留 / 历史库 ≥93。

**同公司同产品代号启发式**："DeepSeek 正式发布 V4 大模型" vs "DeepSeek 推出全新 V4 模型" 字面相似度只有 60 出头，够不到裁决区间。mock 裁判增加规则：相似度 ≥55 且同公司且同产品代号（V4/GPT-5/GB300…的正则抽取）→ 判同事件。真实链路里这类判断交给 LLM。

## §4 评分公式的调参故事

第一版热度加成 `min(0.5, log10(points+1)×0.2)`：GitHub 6 万星的 markitdown 仓库拿到满分加成，把"OpenAI 完成 400 亿美元融资"挤出头条——**热度是社区活跃度，不是行业重要性**，两者不该用一个公式直接竞争。改法：加成上限压到 0.25、斜率降到 0.12，并给数据源加 `headline_eligible` 开关（GitHub Trending 只进快讯）。验证方式：demo 数据重跑，头条变成融资/发布/芯片等真正的行业事件。

这条经验的价值在于：**纯规则可解释，所以能定位"为什么它排第一"；如果是纯 LLM 打分，这类 bug 无从查起。**

## §5 架构重构：mock 客户端的"空转"bug

端到端测试一度出现"非 AI 内容没被过滤、去重没生效"的怪象，排查发现：MockLLMClient 收到的 user 消息是**整段提示词文本**（规则 + 内嵌 JSON），`json.loads` 直接失败 → payload 为空 dict → 所有 mock 在空输入上"正常工作"（返回空列表），而各节点的降级逻辑把这个错误全部掩盖了——分类退化为 other、评分退回规则分，报纸照出，质量静默劣化。

重构：JSON 载荷与规则文本分离，用 `<input>...</input>` 标签包裹，mock 稳定提取；同时 mock 处理后的结果必须通过与真实链路相同的 pydantic 校验。**教训：降级逻辑是双刃剑——它保证可用性，也会掩盖上游 bug；降级必须"记进报告"，并且测试要覆盖"降级没被触发"本身。**

## §6 SQLite 线程安全

publish 节点写库时抛 `sqlite3.ProgrammingError: SQLite objects created in a thread can only be used in that same thread`。原因：LangGraph 把同步节点放进线程池执行，连接在主线程创建。解法：连接参数 `check_same_thread=False` + `threading.Lock` 串行化写操作。连带把 checkpoint 连接也做了同样处理。

## §7 产物打磨的取舍

- **快讯复用摘要**：最初想让快讯编辑重新润色一版"更短的"，后来意识到摘要本身就是 ≤60 字的一句话，再润色是纯 token 浪费且口径可能不一致——删掉这次 LLM 调用，快讯编辑退化为纯筛选排序。
- **昨日回顾**：第一版日报是"孤立的报纸"，加上从归档库取昨日头条的一行回顾后，日报之间有了连续性——一个 SQL 查询换来的产品质感提升。
- **今日微语**：刻意写成"基于头条的洞察"而不是随机鸡汤模板，并在 Prompt 里禁止"加油努力"式空话——日报的人格来自克制的观点。

## §9 真实运行才暴露的坑：async 图 + 同步检查点

demo 与全部 33 个测试通过后，用户首次 `robin run`（真实模式）即抛
`NotImplementedError: The SqliteSaver does not support async methods`。

**根因**：流水线统一用 `graph.ainvoke()`（采集节点是 async httpx），LangGraph 会以异步方式
调用检查点；而真实模式挂的 `SqliteSaver` 只实现了同步接口，`aget_tuple` 直接抛错。
mock 模式的 `InMemorySaver` 同步异步都支持——所以离线链路全程绿灯，问题只在真实模式暴露。

**教训与修复**：
1. 测试替身（InMemory）与生产实现（Sqlite）行为不完全对等——"mock 全绿"不代表生产路径被覆盖
2. 修复：真实模式改用 `AsyncSqliteSaver`（aiosqlite 连接），并把检查点创建移入 async 上下文；
   新增回归测试 `test_async_sqlite_checkpoint`（注入 MockLLMClient 但保留 SQLite 检查点），
   让"真实模式路径"在离线测试里也能跑到
3. 抽象出一条测试接缝原则：**环境差异（真实/离线）应通过依赖注入逐项控制**，
   而不是由单一 mock 开关联动全部替身——否则某个生产替身永远测不到
